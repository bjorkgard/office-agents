## Success criteria (source: docs/designs/office-agents-isometric-office.md, Success Criteria; BUILD_TODO 6.1)

1. `vp dev` shows a live session from an existing transcript within seconds, no config (spec: live smoke, P6-X1; fixture proxy: "a new session takes its seat and works", @live).
2. A subagent shows a visible walk-in and paper handoff (spec: subagent handoff cases in `e2e/office.spec.ts`).
3. Wave and bubble fire on a heuristic attention signal (trailing "?" or open tool call past the timer; spec: "an open tool call past the timer waves" @live, plus @core wave cases).
4. Holds up with 12 agents (spec: @twelve cases plus the M10 perf budget, P6-X3).

Rules derived from the baseline, not new scope: (eng review D2) the live smoke reports PASS if an agent renders within 10 s of page load, FAIL on a refused or unavailable banner, a page error, or an agent that first renders between 10 s and 30 s, and SKIPPED with the reason when nothing renders within 30 s. The earlier "recent session within `STALE_MS`" wording is withdrawn: the feed tracks 4 h (`shared/tuning.ts:6`). A FAIL on criteria 1 to 4 means 6.1 is not done; the one exception is a perf-budget miss, which D8 turns into a dated TODO. T1 records the evidence (scoreboard output pasted into the criteria doc) and ticks 6.1. The Safari pass is recorded in DESIGN.md as a short table (agents, metric, value, date). The scoreboard is run by hand before the version bump; no CI step runs the live smoke. The `@visual` step in T3 is blocked until you approve a push; without it the branch keeps `--grep-invert @visual` and T3 stays open. First M10 Chrome run sets the actual numbers; D8 budgets are the pass line either way.
